# 技术岗简历原则

## 目标

让 ATS 快速识别真实匹配关键词，让招聘方在短时间内看清岗位定位、个人 ownership、技术决策与可验证结果。

## 真实性优先

- 仅使用用户明确提供、材料明确记载或用户确认的事实。
- 团队成果必须写清个人角色：独立负责、主导、参与、协作、支持。
- 禁止补造 QPS、用户数、成本、性能提升、奖项、技术栈或职位级别。
- 无法确认数字时，使用范围、对象、链路、版本、覆盖面等可验证描述。

## Bullet 公式

优先采用：`动作动词 + 做了什么 + 如何做 + 结果/影响`。

示例：

- 弱：负责 Redis 缓存优化。
- 强：重构观看时长 Redis 存储模型，将 3 类独立 Key 合并为 1 个 Hash；配合灰度回填方案，内存使用率从 85% 降至 30%。

可用动词：设计、实现、重构、优化、构建、主导、交付、排查、定位、拆分、治理、自动化、迁移、标准化、监控、验证、分析、压测、修复。

## Bullet 加粗总结（可扫描性增强）

项目经历与长 bullet 列表中，为每条 bullet 句首添加简练加粗总结，格式：`**总结短语**：动作 + 技术 + 结果`。

- 总结短语：12 字以内名词短语或短动词短语，概括本条核心动作/价值，如 `**DDD 三域建模与全链路交付**`、`**责任链 + 分布式锁保障并发一致性**`。
- 同一项目内各条总结保持句式平行（同为名词短语或同为动词短语），不混用。
- 总结不得重复正文细节、不得引入正文外的新事实；正文仍是「动作 + 技术 + 结果」的完整表述。
- 同步在 Markdown（`**…**`）、ATS HTML 与现代 HTML（`<strong>…</strong>`）中实现；Resume IR 中记录为 bullet 的 `highlight` 字段。
- 适用范围：项目经历优先；若经历 bullet 条数少（≤2）或句子本身很短，可不加，避免冗余。

## 技术岗位信息重点

- 后端：接口/服务边界、数据一致性、数据库、中间件、并发、性能、稳定性、可观测性。
- 前端：用户体验、性能、组件/工程化、可访问性、跨端、交付效率。
- 数据/算法/AI：数据规模、指标、评估方法、部署、成本、效果边界、实验设计。
- DevOps/SRE/云：可用性、恢复时间、部署频率、基础设施、成本、监控、事故响应。
- 测试/质量：覆盖率、缺陷、自动化范围、质量门禁、发布风险。
- 安全：威胁模型、漏洞类型、修复闭环、合规、响应时间；不得暴露未公开系统细节或凭据。

## 结构

- 使用倒序时间线。
- 初级候选人：教育、实习/工作、项目、技能、荣誉；拥有强项目时可提升项目位置。
- 有经验候选人：摘要、工作经历、技能、项目/教育；仅保留相关项目。
- 每段经历 3–6 条重点 bullet，消除重复职责。
- 技能按语言、框架、数据/中间件、云与工程、AI/专业领域分类。

## 摘要

保持 2–4 行，包含目标岗位、核心技术、年限或经历标签、一个真实亮点。没有足够证据时不要强行写摘要。

## 参考来源

本指南采用公开职业服务建议的共识：使用具体、主动、可量化、事实导向且可快速扫描的表达；按目标岗位定制并确保 AI 辅助内容真实可解释。主要参考：Harvard FAS / Mignone Center for Career Success 的公开简历指南。
